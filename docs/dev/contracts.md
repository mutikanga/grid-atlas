  Real names from NCC, Planning, GIS or SCADA are mapped to codes through `config/aliases.csv`.
- **Element IDs (canonical; real models keep their own IDs, but synthetic data and hand-built models use these):**
  - bus `<SS>-<kV>-<n>` (`KAW-132-1`)
  - line `L-<A>-<B>-<kV>-<ckt>`, with A and B in alphabetical order (`L-KAW-MUT-132-1`)
  - two-winding transformer `T-<SS>-<n>` (`T-KAW-1`)
  - generator `G-<PLANT>-<n>`
  - load `D-<SS>-<n>`
  - shunt `C-<SS>-<n>`
- **Column names** are snake_case, and the unit is the suffix:

  | Suffix | Unit | Suffix | Unit |
  |---|---|---|---|
  | `_mw` | MW | `_mvar` | MVAr |
  | `_mwh` | MWh | `_mvarh` | MVArh |
  | `_kwh` | kWh | `_kv` | kV |
  | `_pu` | per unit | `_pct` | percent |
  | `_mva` | MVA | `_ka` | kA |
  | `_km` | km | `_c` | °C |
  | `_ugx` | Uganda shillings | `_ugx_per_kwh` | UGX per kWh |
  | `_us_per_km` | µS per km | `_ohm_per_km` | Ω per km |
  | `_ha` | hectares | | |

- **Time and dates:**
  - Months are `YYYY-MM`. Dates are `YYYY-MM-DD`.
  - Date-times are `YYYY-MM-DD HH:MM` in East Africa Time (EAT, UTC+3, no daylight saving).
  - Interval data is timestamped at the **start** of the interval.
- **Yes/no** columns hold `Y` or `N`.
- **Example values** in templates use dummy names (`Example A`, `EXA`, `EXB`, `EXA-132-1`), so nobody mistakes an example for our estimate of a real figure. Never put a real UETCL figure in an example.

## 3. Template specs (`templates/spec/*.toml`)
One TOML file per template is the single source of truth for:
- the Excel workbook sent to the data holder (`templates/<id>_<slug>.xlsx`, generated by `templates/build_templates.py`);
- the loader's validation;
- the generated `ts.*` input tables.

The engine reads input columns by the names defined here, so **renaming a column is a breaking change**.

Validate a spec with:
`docker run --rm -v "$PWD":/w -w /w python:3.12-slim-bookworm python templates/validate_spec.py templates/spec/<file>.toml`

### 3.1 File format
```toml
id = "T03"                       # template id; file name is templates/spec/T03_<slug>.toml
slug = "ncc_monthly"             # workbook is T03_ncc_monthly.xlsx
title = "NCC monthly reporting and metering"
holder = "UETCL NCC: reporting, and metering / energy accounting"
requests = [5, 7]                # request numbers in docs/data-requests/README.md
dataset = "ncc_monthly"          # import dataset code (provenance, criticality)
criticality = "critical"         # critical | high | medium | low
period = "September 2025 to September 2026"
intro = """
README text for the first sheet: what the data is for, the one-line minimum,
'send your native format if easier', how to deliver, the handling rules.
"""

[[sheets]]
name = "system_summary"          # Excel sheet name: snake_case, at most 31 characters
table = "ncc_system_monthly"     # ts table name: unique across ALL specs, prefixed by source
title = "System summary"
format = "xlsx"                  # xlsx (default) | csv | vector | qa
grain = "one row per month"      # what one row means
key = ["month"]                  # natural key; a reload replaces rows with the same key
required_sheet = true            # false = useful but not blocking
notes = "Optional extra guidance shown above the header."
columns = [
  { name = "month", type = "month", required = true, desc = "Calendar month", example = "2026-03" },
  { name = "sent_out_mwh", type = "number", unit = "MWh", required = true, min = 0, desc = "Energy sent out", example = 515600 },
  { name = "method", type = "enum", enum = ["metered", "estimated"], required = false, desc = "How it was obtained", example = "metered" },
]
```
- **Column fields:**
  - `name`, `type`, `desc` and `example` are mandatory.
  - `unit`, `required` (default false), `enum` (mandatory for type enum), and the bounds `min`/`max` (error) and `warn_min`/`warn_max` (warning) are optional.
- **Types:** `text`, `int`, `number`, `month`, `date`, `datetime`, `yn`, `enum`.
- **Format `csv`:** the holder sends CSV files instead of a sheet. Add `file_pattern` (for example `"scada_YYYY-MM.csv"`). The workbook still gets a sheet showing the columns and an example row.
- **Format `vector`:** a GIS layer (GeoPackage, Shapefile with .prj, GeoJSON or KML). Add `geometry` (`Point`, `LineString`, `Polygon` or `MultiPolygon`). The columns are the required attributes.
- **Format `qa`:** a question sheet. Leave `columns` out and give `questions = [ { id = "Q1", text = "..." }, ... ]`. The holder answers in an `answer` column. The rows load into `ts.qa_answer`.
- **Prefixes** for table names: `net_`, `gis_`, `ncc_`, `scada_`, `ops_`, `com_`, `uedcl_`, `plan_`, `site_`, `team_`, `hb_`.

### 3.2 Generated input tables
`ts.<table>` holds the spec columns plus `batch_id bigint` and `row_num int`. Types map as:

| Spec type | Postgres type |
|---|---|
| text | `text` |
| int | `integer` |
| number | `double precision` |
| month | `date` (first day of the month) |
| date | `date` |
| datetime | `timestamptz` (EAT on input) |
| yn | `boolean` |
| enum | `text` |

Unknown columns in a delivered file are ignored and logged. That is how personal or extra fields stay out.

- One Markdown file per request, named `NN-<holder>-<topic>.md` with the request number, for example `05-ncc-scada.md`. Plus:
  - `00-covering-memo.md`, for the sponsor to sign;
  - `handling-note.md`;

- **Each request note has these sections:**
  1. To / From / Date / Due.
  2. Why we need it, in two or three lines, naming the demo item or acceptance check it serves.
  3. What to send: numbered, exact fields, period, granularity and format. Point to the template and its sheets.
  4. Questions to answer.
  5. What not to send: no personal data, no customer names.
  6. How to deliver: per the handling note, with a UETCL share or the server landing folder; never personal email, WhatsApp or personal cloud.
  7. Contact: a placeholder `[name, phone]` for the team member.

  - Fri 6 Nov: critical items (requests 2, 4, 5, 6, 7, 8, 12).
  - Fri 13 Nov: the rest (3, 9, 10, 13, 14).

## 7. Database
- **Schemas.**
  - `meta`: runs, imports, settings.
  - `ref`: substations, aliases, plants, months, holidays.
  - `ts`: inputs, generated from the specs.
  - `gis`: open context layers.
  - `results`: engine outputs.
  - `api`: the ONLY schema the API role can read.
- **Migrations:** `db/migrations/NNN_name.sql`, applied in name order by `engine/migrate.py` and tracked in `meta.schema_migration(filename, sha256, applied_at)`.
  - `001–099`: applied once. A changed file is an error; write a new migration instead.
  - `100–199`: rebuildable. When the file changes, the runner drops schema `ts` with CASCADE and re-creates it, then says "reload inputs".
  - `200–899`: results tables, applied once. In dev, `./atlas reset` starts clean.
  - `900–999`: views. They are re-applied on every migrate (`DROP VIEW IF EXISTS … CASCADE; CREATE VIEW …`), after everything else.
- **Number ranges:**

  | Range | Owner |
  |---|---|
  | 001–009 | F2 |
  | 100 | generated |
  | 210 / 910 | losses |
  | 220 / 920 | validation and reconciliation |
  | 230 / 930 | remedies |
  | 240 / 940 | contingency |
  | 250 / 950 | forecast |
  | 260 / 960 | Kawanda |
  | 270 / 970 | sites and headroom |
  | 280 / 980 | incidents and dashboard |
  | 900 | F2 core views |

- **Roles:**
  - `atlas_rw` owns every schema and is used by the worker.
  - `atlas_ro` is used by the API. It has USAGE on schema `api` and SELECT on its views only, with `default_transaction_read_only = on` and `statement_timeout = 5s`.
  - Views are owned by `atlas_rw`, so `atlas_ro` reads through them without seeing the underlying tables.
- **Run keys:** every `results.*` table has `run_id bigint NOT NULL REFERENCES meta.run(run_id) ON DELETE CASCADE`.
- **Current run:** `meta.v_current_run(run_id)` is the pinned run (`meta.settings` key `pinned_run_id`) if set, otherwise the latest run with status `ok`. Every `api.*` view filters to it.
- **Geometry** is SRID 4326. Distances use geography or EPSG:32636.
- **Core tables (F2):**
  - `meta.import_batch(batch_id, dataset, template, root, provenance, received_from, received_on, adapter, files jsonb, started_at, finished_at, status, rows_read, rows_loaded, rows_rejected, code_version, message)`
  - `meta.import_issue(issue_id, batch_id, sheet, row_num, column_name, severity, rule, message, raw_value, suggestion, raw_row jsonb)`. A row with any `error` issue was rejected: this is the quarantine.

  - `meta.run_input(run_id, batch_id)`
  - `meta.run_stage(run_id, stage, started_at, finished_at, status, n_loadflows, n_failed, message)`
  - `meta.settings(key, value)`
  - `meta.signoff(note, signed_by, role, signed_on, code_version)`
  - `ref.substation(ss_code, name, kv_levels, district, in_central, lat, lon, geom, source)`
  - `ref.alias(alias_norm, entity_type substation|plant, canonical_id, source)`
  - `ref.plant(plant_code, name, technology, ss_code, connection_kv, source)`
  - `ref.month(month, label, days, hours, n_wd, n_nwd, is_forecast)`
  - `ref.holiday(day, name)`

## 8. Data folder and loading (F2 implements, F5 produces)
- **Layout:** `data/<root>/<dataset>/`, where:
  - `<root>` is `synthetic`, `real` or `open`;
  - `<dataset>` is the spec's `dataset` value, which equals its `slug` (`network_model`, `gis`, `ncc_monthly`, `scada`, `ncc_operations`, `commercial`, `uedcl_feeders`, `projects_and_loads`, `sites`, `growth`, `recon_explanations`, `handbuilt_network`, `planning_studies`);
  - open context layers live in `data/open/layers/`.
- **`manifest.toml`** in each dataset folder:
  ```toml
  dataset = "ncc_monthly"
  template = "T03"
  provenance = "synthetic"        # synthetic | approximate | open | real
  received_from = "engine/synthetic"
  received_on = 2026-11-01
  adapter = "template"            # or a module in loaders/adapters/
  [[files]]
  path = "SYNTHETIC_T03_ncc_monthly.xlsx"   # all sheets of the workbook
  sha256 = "..."
  [[files]]
  path = "scada_2026-07.csv"
  sheet = "hourly_data"           # csv and vector files name their sheet
  sha256 = "..."
  ```
  For open layers, each file entry has `layer = "protected_area"` plus an optional `name_field`.
- **Loader rules:**
  - Refuse a file whose sha256 does not match.
  - Refuse `provenance = "synthetic"` under `data/real`, and refuse synthetic loads when `ATLAS_ENV=server` unless `ALLOW_SYNTHETIC=1`.
  - Validate every row against the spec: type, required, enum, min/max are errors; warn_min/warn_max are warnings.
  - Resolve name columns through `ref.alias` into `<col>_code`. An unresolved required name is an error with a difflib suggestion. An unresolved optional one is a warning.
  - Ignore unknown columns, logging them as info.
  - A new delivery replaces existing `ts` rows with the same key, in one transaction.
  - Synthetic xlsx files carry the workbook keyword `gridatlas-synthetic`. CSV and vector files are recognised by the `SYNTHETIC_` file-name prefix.
- **Canonical register files (F2, synthetic defaults now, edited by the team when real data arrives):**
  - `config/substations.csv`: ss_code, name, kv_levels, district, in_central, lat, lon, source
  - `config/plants.csv`: plant_code, name, technology, ss_code, connection_kv, source
  - `config/aliases.csv`: alias, entity_type, canonical_id, source
  - `config/holidays_ug.csv`: date, name
  
  The worker loads them into `ref.*` on every `load` and `run`.

## 9. Engine
- **Config:** `config/engine/*.toml`, one file per owner, merged by `engine/config.py` into `cfg[<file stem>]`. For example, `cfg["losses"]["r_temp_c"]` comes from `config/engine/losses.toml`.
- **Command line (F2):** `python -m engine.cli <cmd>`:
  - `worker`: wait for the DB, migrate, optionally bootstrap (`BOOTSTRAP=synthetic`: synth, load, run --pin), then idle.
  - `migrate`
  - `templates`: build the workbooks and the DDL, then migrate.
  - `synth [--variant base|line_bound|dirty] [--seed 42]`
  - `load [--root data/synthetic] [--dataset X]`
  - `run [--stages a,b] [--pin]`
  - `pin RUN_ID`
  - `scratch NAME`: create database `gridatlas_<name>`, migrate, load `data/synthetic`, and print its `DATABASE_URL`. For agents testing SQL and stages in isolation.
  - `report`: a short text summary of the current run.
- **Stages,** in order: `network, losses, validation, reconciliation, remedies, contingency, forecast, kawanda, sites, incidents`.
  - Each stage is `engine/stages/<stage>.py` with `def run(ctx) -> None`.
  - F2 writes stubs that log "not implemented". Slice owners replace their own stub.
  - A stage that raises is marked failed in `meta.run_stage`, and later stages still run if they do not depend on it.
- **`RunContext` (F2, `engine/context.py`):**
  - `run_id`, `cfg`, `log`
  - `read(sql, params) -> DataFrame`
  - `table(name, where="", params=None) -> DataFrame`, for example `ctx.table("ts.ncc_substation_monthly")`
  - `write(table, df) -> int`: adds `run_id` and bulk-copies into `results.<table>`
  - `inputs`: the cached `engine.inputs.Inputs` (F3b)
  - `net(case_id=None, as_of=None, scenario="base") -> pandapowerNet`: a fresh deep copy from F3a's builder, cached internally
- **Numeric code is pure:** functions take DataFrames or pandapower nets and return DataFrames. Database I/O stays in `engine/stages/*.py`. Unit tests target the pure functions.
- **F3a interfaces:**
  - `build_net(net_tables: dict[str, DataFrame], case_id: str, substations: DataFrame, *, as_of: date | None = None, statuses=("existing", "committed"), r_temp_c: float = 50.0, rating_set: str = "cont", extra: dict[str, DataFrame] | None = None) -> pandapowerNet`. Element `name` = the T01 id; identity columns are added (bus: `bus_id, ss_code, in_central`; line: `line_id, ss_from, ss_to, in_central, length_km, rate_mva, commissioning_year, tower_group`; trafo: `trafo_id, ss_code, in_central, rate_mva`; gen: `gen_id, plant_code, technology`; load: `load_id, ss_code, share`). `max_i_ka` follows the chosen rating, so `loading_percent` is against it.
  - `element_register(net) -> DataFrame` and `bus_register(net) -> DataFrame` produce rows for `results.element` and `results.bus`.
  - `check_net(net) -> DataFrame(severity, element_type, element_id, message)`.
  - `run_pf(net, *, ladder=("results", "dc", "flat"), max_iteration=30) -> PFResult(converged, method, message)`.
  - `element_results(net) -> DataFrame` with columns as in `results.element_result` minus `run_id, case_key`.
  - `bus_results(net) -> DataFrame`.
  - `islanded_load_mw(net) -> float`.
- **F3b interfaces:**
  - `load_inputs(ctx) -> Inputs`, with `case_id`, `net_tables` (all T01-shaped `ts.net_*`, or converted from T12), `substations`, `plants`, `months`, `holidays`, `substation_monthly`, `generation_monthly`, `sample_days`, `scada_points`, `events`, and a method `scada(month) -> DataFrame` that loads one month lazily.
  - `Snapshot(case_key, kind, month, day_type, hour, weight_h, loads: DataFrame[load_id, p_mw, q_mvar], gens: DataFrame[gen_id, p_mw], profile_source, note)`
  - `month_snapshots(inputs, month, cfg) -> list[Snapshot]`. The weights sum to 24 × the days in the month.
  - `peak_snapshot(inputs, month, cfg)`, `min_snapshot(inputs, month, cfg)`, `hour_snapshot(inputs, when: datetime, cfg) -> Snapshot | None`
  - `apply_snapshot(net, snap)`
  - `scale_loads(net, factor, ss_codes=None)`
- **Case keys** are readable: `2026-03|WD|20` for a snapshot, `2026-03|peak`, `2026-03|min`, `2030|peak`, `2026-03|n1|<element_id>`.

## 10. API and web core (F4)
- **API:** FastAPI, GET only.
  - `/api/docs` uses self-hosted Swagger assets at `/vendor/swagger-ui/`. `/api/openapi.json`.
  - Routers are auto-included from `api/routers/*.py`: each module exposes `router = APIRouter(prefix="/api/<area>")`. The export router is mounted at `/export`.
- **Tables:**
  - `api/tables.py` defines `Col(key, label, unit="", decimals=None)` and `TableSpec(name, title, view, columns, filters: dict[param, sql_column], order_by)`.
  - Routers call `register(TableSpec(...))` at import time.
  - `/export/{name}.csv|.xlsx` serves any registered table, with the same filters.

## 13. Real-time adjustment: what-if scenarios and automatic data pickup (team lead, 1 Nov 2026)
The platform must be adjustable while running. This section overrides any "read-only, GET only" wording above, but only in the narrow ways listed here.

### 13.1 What can be adjusted
- **Assumptions:** `config/adjustable.toml` lists every adjustable setting. Each entry has a dotted key into the merged config (for example `losses.r_temp_c`, `n1.rating_set`, `forecast.growth_pct`, `remedies.capex_override`, `valuation.bst_ugx_per_kwh`, `sites.weights.<load_type>.<factor>`), a label, a unit, min/max/step or a list of choices, and the stages it affects.
- **Actions:**
  - trip any line or transformer (N-1 view);
  - add or remove a load of X MW at a site or substation;
  - add a planned project early;
  - switch the data source used (synthetic, public or real).
- **Instant, no recompute:** site scoring weights. `api/scoring.py` already scores per request, so weights are passed as a query parameter.
- **Fast, in the API process:** trip any element. This is a live load flow on the cached case net, with a 3 s timeout that falls back to the precomputed answer.
- **Background jobs:** everything else. Only the affected stages are recomputed. The target is under 60 s for a single-assumption change on the Central model.

### 13.2 Scenarios
- **The baseline is never changed by a what-if.** A scenario is `meta.scenario(scenario_id, name, base_run_id, overrides jsonb, actions jsonb, created_by, created_at, status queued|running|done|failed, result_run_id, message)`.
- **Queue:** `meta.scenario_job` is the queue. The worker uses `LISTEN atlas_jobs`, with a 5 s poll as fallback. It copies the base run's untouched results by reference, re-runs only the affected stages into a new `meta.run` (`kind = 'scenario'`, `scenario_id`), and never pins it.
- **Every stage** must read its thresholds through `ctx.cfg`, which the scenario overrides are merged into, and must honour `ctx.actions` where relevant (extra loads, outages, early projects). Never read config files directly inside a stage.
- **Views change:** every `api.*` view exposes `run_id` and does **not** filter to the current run. `api/render.py` adds `run_id = :run`, where `:run` is the request's `?run=` (a scenario's result run) or, by default, `meta.v_current_run`. Each page can therefore show a baseline, a scenario, or the two side by side.

### 13.3 Who may adjust
- **Roles:** viewers need no login. Editors sign in.
- **Users:** `data/auth/users.json` (git-ignored) holds `{username: {scrypt_hash, salt, role}}`. It is created with `./atlas user add NAME`. Session cookies are HMAC-signed with `ATLAS_SECRET` from `.env`, `HttpOnly`, `SameSite=Strict`, and expire after 8 hours.
- **Write role:** the new database role `atlas_scn` has INSERT/UPDATE on `meta.scenario` and `meta.scenario_job` only, and nothing else. The API uses it only for scenario endpoints. `atlas_ro` stays read-only.
- **Allowed writes:** Nginx allows POST only on `/api/auth/*` and `/api/scenarios*`, with a CSRF token header. Everything else stays GET/HEAD.
- **Audit:** every scenario records who, when and what changed. `GET /api/scenarios` lists them.

### 13.4 Automatic data pickup
- **Inbox:** `data/inbox/<root>/<dataset>/` is a drop folder (root = real | public | synthetic). The worker scans it every 60 s. When a file is new or changed, it:
  1. writes or refreshes `manifest.toml` (sha256, received_on);
  2. moves the files into `data/<root>/<dataset>/`;
  3. loads them;
  4. runs the affected stages as a new baseline run.
- **Pinning:** the new run is pinned automatically when `ATLAS_AUTO_PIN=1` (the default in dev) and every critical import is `ok`. Otherwise it waits for `./atlas pin` and the page shows "new data loaded, not yet published".
- **Status:** `GET /api/meta/status` reports the latest import, the latest run, the pinned run, the queue length and whether data is being processed. Pages poll it every 15 s and show a small "updated hh:mm" note.

### 13.5 Web
- **Adjust panel:** `web/js/adjust.js` and `web/css/adjust.css` provide a side panel on every page:
  - sign in;
  - a scenario selector (Baseline plus saved scenarios);
  - controls generated from `/api/scenarios/adjustable` (from `config/adjustable.toml`);
  - "Run" with progress;
  - "Compare with baseline";
  - "Save as".
- **Sections:** they receive `ctx.run` (the run to show) and `ctx.compareRun` (optional). They must pass `run` on every API call and re-render when `ctx.onRunChange` fires.

### 13.6 Owners (wave 2b, after wave 2)
- **R1 scenario backend:**
  - `api/routers/scenarios.py`, `api/routers/auth.py`, `api/auth.py`
  - `engine/scenarios.py`, `engine/watcher.py`

- **R2 adjust panel:** `web/js/adjust.js`, `web/css/adjust.css`, `tests/unit/web_adjust/`.
- **R3 integration** of 13.2 into the wave-2 code (render `?run=`, views, worker loop, nginx POST rule): the lead.
